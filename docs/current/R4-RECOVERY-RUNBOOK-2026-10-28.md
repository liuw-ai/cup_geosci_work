# R4 恢复与只读审计手册（2026-10-28）

## 当前事实

- `749` 是 2026-10-24 线上 R4 回执中的学生端汇总，不是本机 `runtime/job_hub.sqlite3` 的快照。
- 本机已发现的 SQLite 快照中没有 `job_hub-20261024T052020Z.sqlite3`，也没有总量为 4494/4496 的 R4 数据库。
- 回执记录的服务器路径为 `/var/lib/job-hub/backups/job_hub-20261024T052020Z.sqlite3`。该路径只能在服务器上读取；当前没有服务器 SSH、备份文件或逐岗位导出，因此现在不能逐条恢复 749。

## 恢复条件

需要满足以下任一条件：

1. 从服务器取得该 SQLite 文件的只读副本；或
2. 从线上导出包含岗位主表、来源证据、发布时间/截止日期、发布状态和详情键的逐岗位 JSON/CSV。

仅有 `749` 这个数字、release tag 或回执文本，不能恢复岗位明细，也不能推断哪些岗位被阻断。

## 安全操作顺序

1. 在服务器停止写入或使用 SQLite online backup 生成副本，不直接复制运行中的 WAL 主库。
2. 下载副本后计算 SHA-256，记录文件大小、生成时间和服务器路径；原文件保持不变。
3. 将副本放入本机 `APP_DATA_DIR` 管理的备份目录，文件名保留 R4 时间戳。
4. 先执行 `verify-backup` 和只读 `integrity_check`，确认 `sources`、`jobs`、`service_heartbeats` 表存在。
5. 在隔离副本上生成逐岗位审计：当前开放、已过期、重复/替代、`student_eligible`、`pending_evidence`、`out_of_scope`、来源暂不可用。
6. 将审计结果与本地 canonical read path 分开报告；未经逐岗位去重和证据核验，不把 R4 的 749 与本地 495 相加或相减。
7. 只有用户确认恢复目标、停止 Web/Worker 并完成紧急备份后，才允许执行受管恢复命令。恢复不是发布，恢复后仍需重新跑 Phase 7.2 门禁。

## 当前阻塞

本机可以完成第 3 步之后的验证和审计，但无法替用户取得第 1 步的服务器文件。因而 `749` 目前是“可恢复但缺少输入材料”，不是“已经恢复”。

# 岗位阻断与项目现状审计

日期：2026-10-27（Asia/Shanghai）  
性质：只读审计；本报告没有部署、没有修改生产数据库、没有修改生产密钥。

## 一、需求与目的

这个项目的实际目标不是把抓到的网页数量做大，而是建立一个面向地球科学学院学生的、持续更新的就业信息服务：

1. 尽可能覆盖企业校园招聘、事业单位、公务员、科研院所、高校和博士后等与学生相关的岗位。
2. 每条公开岗位都能回到官方公告、官方详情页或官方附件的岗位级证据。
3. 清楚区分“当前开放”“已截止”“待核验”“不属于学生范围”和“仅作为发现线索”，让学生知道哪些信息可以直接使用、哪些必须自行复核。
4. 第三方职位表和聚合渠道用于发现漏网信息，不直接替代官方来源。
5. 在不放宽专业、学历、地点、截止日期和官方证据门禁的前提下，逐步扩大真实可用的学生端岗位量。

因此，“岗位总数”不是最终指标；更重要的是当前开放岗位、学生端公开岗位、待核验岗位和明确排除岗位之间的可解释漏斗。

## 二、Phase 7.2 是否完成

结论：**尚未完成，也不能称为已完成。**

已完成的是本地候选代码和测试准备：第三方线索可以绑定 `official_source_id`，管理员核验通过的线索可以复用同一套学生发布门禁，管理员/增长指标/发现漏斗可以显示第三方漏斗，学生端不会直接暴露第三方线索。

追加代码复核发现：Web 管理台和管理员 API 会把 `database.list_third_party_batches()` 传入漏斗，但 CLI 的 `discovery-funnel` 和 `growth-metrics` 分支没有传入批次数据。因此当前正式本地库即使未来写入批次，CLI 仍可能显示 `batch_count=0`；本次实际 CLI 输出也为 0 个批次。该问题尚未修改，Phase 7.2 发布前需要补齐 CLI 集成和端到端测试。

进一步检查 R4 回执对应的 Git tag `release-2026.10.24-r4`（SHA `1f3a3b8b7d30e193107b16c8d6b86c81969057fd`）发现，其 `job_hub/db.py` 也包含同样的 `publication_status IN (...) OR publication_layer IN (..., 'incomplete_but_basic_match', ...)` 条件。因此可以确认 R4 存在同一代码路径风险；但没有 R4 数据库，仍不能把本地 436/25/5 的数量直接套到线上 749。

未完成的是发布闭环：

- 线上仍是 `phase7-20261024-r4`，R4 回执记录为检查 4,494 条岗位、当前学生端公开 749 条；另一份夜间回执检查量为 4,496。工作区没有 R4 生产 SQLite 副本，无法逐岗位重算这 749 条。
- Phase 7.2 的代码修改仍是本地未提交工作区变化，包含 `job_hub/app.py`、`job_hub/discovery.py`、`job_hub/third_party_tables.py`、`job_hub/worker.py` 和新增的 `job_hub/lead_publication.py`、测试与阶段文档，尚未形成 release、推送、备份服务器数据库或部署。
- R4 回执的生产就绪状态仍为 `false`：来源新鲜度、政府台账新鲜度、57 条政府附件证据、公网 TLS 稳定性和管理员 bootstrap 密码轮换均未全绿。

所以 Phase 7.2 目前是“本地候选实现 + 定向验证”，不是“已上线完成”。

## 三、4000 多条与学生端 700 多条的真实关系

### 线上 R4（只能确认回执口径）

| 指标 | 回执值 | 能否逐岗位核验 |
|---|---:|---|
| 数据库审计检查量 | 4,494（另一回执 4,496） | 不能，缺生产库副本 |
| 当前学生端公开岗位 | 749 | 不能，只有汇总回执 |
| 生产就绪 | false | 可以，由回执确认 |

因此，线上“约 4,500 条”不是“约 4,500 条学生可投岗位”；749 条是经过学生端发布门禁、日期和去重口径后的公开集合。剩余记录必须再分为不在服务范围、证据不足、已截止/撤回/被替代等类别，不能笼统说成“被系统吞掉”。

### 为什么另一份本地快照不同

`runtime/job_hub.reindexed-before-phase5-baseline-restore-20261022.sqlite3` 同样有 3,956 条，但全库为 `student_eligible=553`、`pending_evidence=910`、`out_of_scope=2,493`；按当前日期开放口径为 `student_eligible=497`、`pending_evidence=741`、`out_of_scope=2,288`。

两份快照总量相同而发布状态不同，说明历史规则重算、证据重建或状态恢复改变了分类。没有线上快照之前，不能把任何一份本地数字冒充 R4 的逐岗位事实；后续必须统一快照、业务日期、去重和截止日期口径。

本轮新增了只读命令 `job-blocker-audit`，可复现上述漏斗：

```text
.venv-rebuilt\Scripts\python.exe -m job_hub.cli job-blocker-audit --as-of 2026-10-27 --sample-limit 5 --output runtime/job-blocker-audit-2026-10-27.json
```

正式本地库本次命令还揭示了一个必须保留的差异：数据库原有学生端读路径按 2026-10-27 返回 675 条；按当前代码重新评价岗位门禁并按官方 detail key 去重得到约 427 条“重算可通过”记录；持久化发布状态与当前重算结果有 763 条当前记录不一致（全库 804 条）。这不是线上学生端数量，也不是可以直接发布的 427 条，而是说明需要在隔离副本先完成规则重算、审计和回归，再决定是否修复持久化状态。

对另一份重建快照运行同一命令，得到 `current_record_count=3526`、持久化状态 `student_eligible=497 / pending_evidence=741 / out_of_scope=2288`、数据库学生端读路径 `833`、重算可通过去重约 `445`、当前状态不一致 `356`。这进一步证明：总量相同不能推出学生端数量相同，历史重建和规则状态必须绑定快照哈希后再比较。

## 五、第三方渠道为什么没有形成数量增量

结论：**不是完全没做，而是做到了“发现和留存”，没有做到可批量、可持续地完成“第三方行 -> 官方逐行证据 -> 学生端发布”。**

正式本地库的线索表有 12 条：9 条已发布、2 条已核验但被学生门禁拒绝、1 条仍是未找到官方 URL 的候选。它们是历史人工核验线索，不等于 Phase 6/7.2 的新批次增量。

Phase 6 隔离库中的华图甘肃财贸职业学院批次只有：解析 12 行、生成 11 条候选、发布 0 条。11 行主要是设计学、食品科学与工程、应用经济学、管理科学与工程、马克思主义理论等博士岗位，不属于当前地学目标专业；因此 0 发布是专业门禁的真实结果，不是程序漏发。

第三方链路的硬阻断包括：

1. `u3.huatu.com` robots 为 `Disallow: /`，不能用自动爬取绕过；只能由管理员合规提供文件或找到官方原文。
2. 聚合表常有单位、岗位、地点、专业、学历和截止日期混在公告级文本中，不能证明每一行属于同一岗位。
3. 同一个第三方职位表可能已经截止，或者官方附件无法访问、动态页面需要浏览器/人工操作。
4. 找到官方 URL 还不够；还必须登记官方来源域名、确认官方内容、补齐岗位级专业/学历/地点/截止日期，再过学生发布门禁。

Phase 7.2 的自动转换代码解决的是“已核验线索不要靠人工再次点击才能进入统一门禁”，没有解决“全国第三方表能持续获得官方逐行证据”这个外部事实瓶颈。因此它是必要的流程改进，但不会凭空制造岗位数量。

## 六、事业编和公务员渠道为什么没有突破全国覆盖

结论：**已经做了局部台账和证据链，但没有完成全国来源矩阵和逐行证据规模化。**

`data/source_targets.json` 对 31 个省份、5 类入口共 155 个目标格统计为：`verified=19`、`candidate=38`、`unlocated=98`。按角色汇总，已验证的自然资源入口 8 个、地调/地勘单位 7 个、人社/考试入口 2 个、公务员入口 2 个，事业单位公开招聘入口仍为 0 个已验证格。

`data/government_position_registry.json` 的 `as_of` 是 2026-09-27，只有 12 个来源评估（7 个已验证开放样本、3 个验证但没有当前匹配、1 个夹具来源、1 个来源不可用）、23 个批次、9 条岗位记录。政府附件清单共 17 个，其中 9 个仍待服务器下载、5 个历史关闭、2 个已核验但不属于学生范围、1 个人工核验。

全国公务员入口目前存在连接拒绝/反自动化和年度职位表未确认的问题；历史职位表或只证明入口可访问，不能当作 2026/2027 年仍在招的地学岗位。事业单位岗位还经常缺少岗位级地点，不能把机构地址推断为岗位工作地点。

所以当前困境不是“全国没有事业编和公务员岗位”，而是每一条可公开岗位都需要当年度公告、正式附件、岗位行、专业、学历、地点和截止日期共同成立；这条证据链尚未全国化。

## 七、换机后的环境与配置风险

1. 旧 `.venv/pyvenv.cfg` 仍指向旧电脑的 `F:\anaconda03\python.exe` 和旧工作区路径，不能继续使用。
2. 当前 `.env` 仍是示例域名、示例密钥和示例管理员令牌，绝不能用于生产；域名审核完成后还需要重新生成真实密钥并轮换 bootstrap 密码。
3. 当前重建环境基于 bundled Python 3.12.14，不等同于历史记录中的 Python 3.11 生产环境；定向测试可复现，但正式发布前应按锁定依赖重建目标版本。
4. 此前的 `1169 passed, 1 failed, 4 skipped` 属于日期夹具修复前的历史结果；本次重新运行全量测试为 `1172 passed, 4 skipped`。仍有既有弃用警告和一次 Windows 控制台编码警告，且测试环境为 Python 3.12.14，不等同于历史生产 Python 3.11。

## 八、当前版本已经具备的能力

- 官方来源注册、抓取、规范化、去重、来源运行记录和岗位生命周期管理。
- 以岗位级证据为核心的学生发布门禁：专业、学历、地点、工作经验、岗位类型、国内范围和截止日期分别判断。
- `student_eligible`、`pending_evidence`、`out_of_scope` 等持久化状态，以及学生端和管理员端分离；第三方发现内容仍保持私有。但本地正式库复核发现，普通学生读路径的兼容条件把 466 条待核/过期记录带入 675 条读路径结果，因此“待核验完全不会进入学生端”不能作为当前事实，必须先修复读路径和测试。
- 浏览器捕获、官方附件处理、岗位表行定位、哈希和证据留存基础。
- 第三方线索表、官方回溯、候选状态、转换事件和发现漏斗；Phase 7.2 新增的自动转换会复用同一发布门禁。
- 部分企业、科研院所、地调单位和省级自然资源来源，以及安徽、湖北、甘肃、宁夏、中国地震局等政府岗位台账的局部样本。
- 备份、数据库审计、来源健康、覆盖率、生产就绪检查和回滚记录。

## 九、尚未解决的核心问题与对应方案

### 1. 线上事实无法逐岗位复核

**问题**：只有回执，没有 R4 SQLite 或逐岗位导出；无法证明 749 条中哪些仍开放、哪些重复、哪些来源已过期。  
**方案**：从服务器取得只读 SQLite 备份或脱敏岗位导出，记录 SHA-256；固定业务日期和去重规则，生成线上阻断报告。没有这一步，任何“线上剩余岗位原因分布”都只能是假设。

### 2. 统计口径不统一

**问题**：总库、`open`、截止日期有效、学生公开、待核验、私有候选和历史快照被混在一起。  
**方案**：在报告和 API 中固定六个指标，并为每个指标明确 SQL 条件；所有展示数字同时带 `as_of`、快照哈希和是否去重标记。

### 3. 待补证据没有按“可修复价值”排序

**问题**：825 条待核验中，有的只是缺地点，有的缺专业/学历字段，有的本质是相关专业或方向不明，人工投入回报不同。  
**方案**：分为“补一项即可复核”“需要重新抓官方附件”“即使补证据也大概率排除”三类，优先处理明确地学岗位、当前开放、截止日近、官方附件可访问的记录；每次补证据后重新运行同一门禁。

### 4. 第三方渠道缺少官方回溯产能

**问题**：第三方解析已经有了，但官方 URL、官方域名绑定和岗位级字段回溯依赖人工，无法批量扩张。  
**方案**：保留第三方发现只读层；为每个批次建立“官方 URL 命中率、官方核验率、字段完整率、专业通过率、发布率、阻断原因”指标；只对官方入口稳定、允许合规访问的来源开发适配器，不绕过 robots、登录或验证码。

### 5. 全国事业编/公务员来源矩阵完成度低

**问题**：155 个目标格中 98 个仍未定位，事业单位招聘角色没有验证格；已定位来源也有附件下载和新鲜度问题。  
**方案**：按省份和角色分批推进。先完成已存在官方证据的 19 个 verified 格，再为每个省补一个可复核的事业单位/公务员官方入口；入口可达不等于有岗位，必须继续做到年度公告和岗位行证据。

### 6. 来源新鲜度和历史岗位清理不稳定

**问题**：线上 readiness 明确未通过来源新鲜度和政府台账新鲜度。  
**方案**：把来源成功捕获、公告 `as_of`、截止日期、无截止日期的有限保鲜期分开监控；过期记录保留审计历史但从当前集合撤下，不修改历史证据。

### 7. 公网、域名和管理员安全门禁未完成

**问题**：域名仍在审核；R4 曾有外部 TLS 重置，`.env` 是示例值，bootstrap 密码尚未轮换。  
**方案**：备案/域名通过后再配置真实域名；由服务器侧重新生成密钥、管理员密码哈希和 token，做外网 IPv4/IPv6/TLS/移动网络检查；不要把真实密钥写入仓库。

### 8. 换机后版本和依赖不一致

**问题**：旧虚拟环境失效，新环境是 Python 3.12，历史生产记录为 Python 3.11。  
**方案**：根据锁定文件重建目标 Python 版本，保存 `pip freeze`/镜像摘要，重新跑定向、全量和浏览器测试；先修复日期不稳定测试夹具，再判断发布。

### 9. 管理员工作台有能力，但缺少运营闭环

**问题**：现在可以看到候选和漏斗，但还没有形成“每日待办、优先级、处理结果、复核人、复核时间、撤回原因”的稳定队列。  
**方案**：增加只读审计报表和管理员待办视图，任何发布/拒绝/撤回都写入事件；不改变学生端门禁，只改善补证据的人工作业顺序。

### 10. 信息采集与学生触达尚未闭环

**问题**：R4 夜间回执显示日报邮件投递为 `skipped`，原因是生产配置关闭邮件；学生只能主动访问网站，无法获得岗位新增、截止日临近和来源失效提醒。  
**方案**：域名和管理员安全门禁完成后，再配置经过验证的 SMTP 或站内订阅；先提供按专业、学历、地区和截止日期的站内筛选与“最近更新/即将截止”视图，再启用低频邮件提醒，并保留退订和失败重试记录。邮件触达不能绕过学生端公开门禁。

## 十、建议执行顺序与验收标准

1. **数据真相层**：获取线上只读备份，生成线上逐岗位阻断报告；在此之前不对 749 条做具体归因。
2. **口径层**：统一当前开放、学生公开、待核验、明确排除、历史和候选六类数字，并在接口返回快照时间和哈希。
3. **高价值补证据**：优先处理已明确为地学、官方附件可访问、仍在报名期的待核记录；每批输出新增公开数和拒绝数。
4. **政府来源扩张**：先补 verified/candidate 中有真实入口的省份，再处理 unlocated；事业单位和公务员分别计数，不能用入口数量代替岗位数量。
5. **第三方漏斗运营**：选择 2-3 个允许合规访问且官方回溯成功率高的渠道做适配器，连续两个周期验证发布率后再扩展。
6. **学生使用闭环**：先把已公开岗位按专业/学历/地点/截止日期做可解释筛选，再配置站内订阅和邮件提醒；以“有效岗位被看到并及时申请”而不是总抓取量衡量价值。
7. **环境与生产门禁**：目标 Python 版本、依赖、域名 TLS、管理员密码、备份、回滚和邮件配置全绿后，才评审 Phase 7.2 release。

当前最需要的外部材料只有一项：**服务器上 R4 数据库的只读备份或岗位导出**。在拿到它之前，继续改抓取代码不会解决“线上 4000 多条中哪些被阻塞”的事实缺口。

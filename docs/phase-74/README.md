# Phase 74：生产运行保护与上线门禁

## 目标

在继续扩大三桶油、事业编和公务员来源前，建立可验证的运行保护：数据库可一致备份、可受控恢复、备份失败不会被健康检查掩盖，并且可以用一条只读检查判断是否满足正式公开发布条件。

这一步服务于学生端可靠性，而不是制造岗位数量。任何新增来源都可能带来解析错误、字段错误或误清退风险；没有已验证回退点，就不应扩大自动采集范围。

## 交付

- SQLite 在线备份：使用 SQLite backup API，不在 WAL 运行期间直接复制数据库文件；
- 私有备份目录：必须位于 `APP_DATA_DIR` 下，不会由学生端路由提供；
- 每份快照：`integrity_check`、核心表校验、SHA-256、原子替换和保留期清理；
- 受控恢复：只能从受管备份恢复，必须显式 `--confirm`，并尝试先保存当前数据库的紧急快照；
- Worker：同步前在备份到期时创建快照。备份失败则暂停本轮会写入岗位库的同步、降级心跳并触发现有邮件异常告警；
- `/healthz`：公开最小化备份状态，不泄露服务器上的备份路径；
- `production-readiness`：同时核验岗位审计、Worker 心跳、备份新鲜度和可选的域名 HTTPS。

## 非目标

- 不修改或导入学生端岗位；
- 不把来源可访问、数据库备份成功或域名已配置误报为岗位增长；
- 不绕过招聘系统 robots、登录、验证码或访问策略；
- 不在本阶段宣称服务器已完成 72 小时或 7 天连续运行验证。

## 上线硬门禁

全院公开发布前必须执行：

```bash
docker compose exec -T web python -m job_hub.cli production-readiness \
  --domain-hostname jobs.cupdky.cn \
  --expected-ip 81.70.62.174 \
  --require-public
```

只有结果 `ready: true`，才代表审计、心跳、备份、DNS 和 HTTPS 同时通过。DNS 为 `NXDOMAIN`、备份过期、Worker 降级或岗位审计失败均不通过。

# 参考项目借鉴记录

本阶段只把参考项目中有助于可维护性和可审计性的做法迁移到本项目；没有把“反爬绕过”当作岗位来源，也没有把第三方聚合结果直接发布给学生。

| 参考项目 | 借鉴内容 | 本项目落点 | 明确不采用 |
| --- | --- | --- | --- |
| JustHireMe | 来源适配器契约、来源元数据、失败可追踪、质量门禁 | `sources.py`、来源注册表、入口探测状态和发布前审计 | 第三方搜索结果直接成为正式岗位 |
| wehire-monitor | 发现线索到核验的状态机、增量监控、失败重试和人工复核队列 | `discovery.py`、`candidate_leads`、Phase 5 私有漏斗；Phase 9 保留失败证据 | 公众号文章直接展示给学生 |
| Firecrawl | 公共动态页面、附件解析、增量和失败重试的工程思路 | Phase 2 附件流水线、Phase 7/9 动态壳分类和专用适配器排期 | 未核验 robots/条款下的整站批量抓取 |
| Scrapling | robots 管理、缓存/限速、抓取器与解析器分层、改版后需回归 | `SourceHealthProbe`、`PublicEntryProbeRunner`、离线 fixture 和有界重试 | stealth、代理轮换、Cloudflare/验证码求解 |
| curl_cffi | 可作为未来合规 TLS/HTTP2 兼容性诊断候选 | 当前先用 `requests` 的 `environment/direct` 诊断分层 | 浏览器 TLS 指纹伪装或绕过 WAF |
| WechatSogou | 公众号文章元数据结构化发现 | 私有 `discovery_sources` 和线索归因 | 搜狗/微信文章作为学生端官方证据 |

## 为什么这能改善“岗位太少”

此前入口失败没有明确区分代理故障、站点策略和页面结构，导致工程上无法安全判断下一步。Phase 9 以后，每个来源都可以沿着同一条证据链排查：

```text
传输模式诊断
  -> robots/入口状态
  -> HTML、公开 API、ATS 或官方附件类型
  -> 专用字段适配器与离线夹具
  -> 原文/附件证据审计
  -> 发布或进入人工复核
```

这不会凭空制造岗位，但会让服务器部署、人工补录和后续逐站适配有可靠入口。真正增加国内岗位仍需逐个接入油田、研究院、工程技术单位和省级官方公告；访问受限来源必须走官方允许的公开路径或管理员核验，不可用技术绕过替代数据真实性。

## 参考经验的适用边界

参考项目的通用能力可以复用，具体站点的访问政策、页面结构和招聘字段不能假设相同。每个新来源必须单独保存主体、当前栏目、robots/条款、列表/详情、附件、字段证据、去重键和回归测试；这正是后续扩大国内岗位覆盖的最小维护单元。
